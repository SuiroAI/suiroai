# DSC-26 review of DSC-24 draft.1

2026-10-17 · review only; **snapshot not yet acknowledged for adapter implementation**.

Reviewed `/private/tmp/suiroai-dsc24/src/suiroai/contracts/schema/retail-contract.schema.json`, version `0.1.0-draft.1`, SHA-256 `cdcddc358a515b8b6a9546f540ac399de94f9de7047aa5957bc5d2fb577992ac`, and the corresponding `validation.py`. This is an exact draft review, not a claim about subsequent owner revisions. The draft was read in its owner's worktree; no uncommitted shared source was copied or edited.

The draft preserves useful immutable artifact/proposal/approval references, approved-assumption comparison, mock provenance, development availability checks, and typed execution errors for invalid code, timeout, cancellation and exhaustion. These are suitable foundations. The adapter still needs these agreements from DSC-24 with DSC-3/10:

1. **Preapproval engineering discovery.** `capability_result` requires an `approved_binding`, and `validate_handoff()` treats capability/evidence records as execution-derived and requires an approved execution contract. Engineering discovery is explicitly allowed before customer sign-off. Either represent that separate scope without customer approval, or explicitly agree a separate discovery record format. Do not fabricate a customer proposal/approval to serialize a probe. Current DSC-26 logs are clearly marked observations outside the shared schema.
2. **Exact execution and parent permission.** `stage_result` has a stage enum and task/run bindings, but no immutable `execution_contract_ref`, parent permission reference, or stage attempt identity. Customer sign-off is not DSC-10's execution permission. Agree schema fields or explicit call arguments binding each attempt/result to the exact execution contract and parent authorization, so changed limits/actions or stale attempts cannot satisfy a checkpoint.
3. **Bounded stage call.** Whole-run `allowed_actions`, `source_refs` and `max_execution_seconds` do not specify the stage's released input allowlist, deadline/remaining limits, or output namespace. Agree the minimal stage call/release interface with DSC-10. This implements bounded portions of the same approved task; it must not introduce a new task-definition/sign-off stage. Existing preparation availability checks are useful but cannot by themselves restrict what files the executing host can access.
4. **Inspectable non-success.** Generic `stage_result` permits `validation_failed` with `failure: null` and empty evidence, and input/material-fact outcomes without a targeted gap. Require outcome-appropriate details/evidence through schema conditions or semantic checks: real measured-failure references, actionable missing information, native execution error evidence, and partial-output usability. Report-layer failed-score checks do not establish a generic stage-result requirement on their own.

For eventual capability acceptance, agree what referenced evidence must contain: actual host and Data identity, accepted explicit skill attachment, native thread/turn identifiers, executed code/output, retrieved artifact bytes/hashes, and bound source/task/run versions. A `supported` boolean plus nonempty evidence arrays is not independently sufficient. Host-specific details can remain referenced evidence; no Data endpoint or broader runtime is requested.

DSC-24 remains the sole schema/validation owner. DSC-26 requests these changes through the owner and will re-review the resulting exact snapshot. The [native startup blocker](DISCOVERY.md) independently prevents real adapter acceptance, regardless of mock/schema test results.

Owner clarification received after the review: DSC-24 agrees that discovery logs remain engineering evidence outside customer `stage_result` instances, and that the observed failure is a runtime startup error rather than plugin absence or validation failure. This resolves the immediate discovery-serialization concern without inventing customer approval. Exact stage permission/bounds/result requirements above still need owner agreement.
