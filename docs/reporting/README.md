# DSC-29 evidence-backed report drafts

This consumer uses DSC-24 `0.1.0-draft.3` without changing shared contracts. Ownership is limited to `src/suiroai/reporting/`, `tests/reporting/`, and `docs/reporting/`; numerical work stays in replenishment. There is no model training, selection, independent runtime, customer messaging, parent transition or delivery permission here.

`draft_success(handoff, artifact_id=...)` requires passed final validation, trusted parent confirmation of that result and the exact approved quantity artifact, and typed accepted independent evidence checking its earlier immutable candidate. The final-validation decision must attest checkpoint `final_validation`; quantity approval must attest `recommendations`. Handoff validation verifies the complete source/version contract graph, and every claimed evidence chain resolves external source bytes against their immutable hashes before humanizing. Approval cannot be supplied as a boolean to the report function. Every approved row and exception is copied without recalculation. Product/store source IDs are displayed, along with the exact approved `product_name` when supplied. No name is inferred. Unsafe control characters, markup or code in names are rejected instead of rewritten.

The report includes the synthetic operations disclosure; the full list with exact approved quantities, units and dates; unresolved per-key exceptions; upstream customer-facing preparation, generated-feature, comparison and unseen findings; declared generated-feature names, rationale and availability; actual baseline/candidate/unseen metric values, populations and observation coverage; the frozen choice; and evidenced material limitations. Missing findings or limitations block drafting rather than inviting invented prose. Findings must already be concise customer-facing sentences. Internal findings, expressions, code and diagnostic logs are excluded. Report claims carry exact immutable source references, including the originating typed finding record.

The optional `humanizer` callable receives a copy of all supported claims and returns a permutation of their IDs. It can organize their presentation but cannot remove a claim, alter a quantity, introduce a name or fabricate a benefit. An independently supplied LangChain structured-output runnable can satisfy this focused callable interface. No real LangChain/provider call or runtime capability is asserted by this implementation or its tests. Unrestricted generated prose remains outside this bounded renderer. An upstream final-report finding is trusted only inside the validated, parent-authorized evidence chain; DSC-30 still independently checks every finished claim against its sources.

`draft_validation_failure` requires measured failed final validation and trusted concluded parent review (`confirmed_failure` or `stop`) at the exact `final_validation` checkpoint. It preserves actual failed scores, states each predeclared gate's direction/threshold/population/aggregation/minimum observation count, names required-check outcomes, and emits no quantity list. An unresolved execution defect is routed to the execution path. `draft_execution_failure` requires an exact typed failed-stage reference and trusted terminal parent review at that stage's checkpoint. It retains the exact concise observed failure reason and error category. Code, multiline diagnostics or oversized reasons block drafting and require an upstream concise reason; they are never silently truncated into a different fact. Neither path retries, selects a fallback model, invents results or declares universal impossibility. Both say this MVP could not produce a reliable solution with the supplied data and scope.

`draft_missing_inputs` returns the exact blocked proposal goal, specific material gaps and their original requests from a proposal or observed stage, without approval, execution or an order list. Supported work is restricted to read-only inspection of actually accessible supplied sources, listed by original filename and declared role. If none are accessible, it says so. The next step asks for the documented facts/files followed by review of an updated proposal for the same business goal; no narrower forecast is silently offered. Its local guidance envelope is explicitly distinguished from a shared `report_draft`: DSC-24 currently requires an execution contract even for that report kind's `missing_inputs` variant, while genuine pre-signoff missing-input assessment has no execution. Supporting a native pre-execution shared report envelope is a contract-owner integration request. We do not fabricate an approved execution to bypass it.

For schema compatibility, a report copies the prerequisite quantity/failure record's existing parent decision. That decision attests its prerequisite only. It does not approve the new report or authorize customer delivery. DSC-30 must independently verify the new exact report version and DSC-10 must authorize its permitted response.

The tests consume explicit DSC-24 mock chains with `allow_mock=True`; production Handoffs reject mocks by default. These fixtures prove consumer behavior only, never upstream execution, useful real model performance or MVP acceptance. Real integration still needs authentic DSC-26 execution evidence, DSC-27/28 artifacts, parent-approved independently verified quantities and DSC-30 final checks.

Run component checks from the application root with `PYTHONPATH=src python -m unittest discover -s tests/reporting -v`.

[MOCK_DRAFTS.json](MOCK_DRAFTS.json) contains reproducible success, measured
validation-failure, execution-failure and missing-input examples returned by
these functions using `tests/reporting/test_drafts.py`'s explicit mock handoffs.
Every draft is unverified for delivery. The success example consumes the
DSC-24 mock numerical approval, not the separate replenishment example's
candidate. Claims and exact artifact references are retained for inspection.
