## Open integration gates

1. **Safe preparation release requires owner action.** DSC-27's trusted, post-approval partition prelude must read the raw sales source outside the native task, retain the reserved December artifact and release only derived permitted development data to native preparation. The current draft.3 semantic validator rejects an externally referenced derived development artifact as a preparation-stage release because it is neither an approved source reference nor an internal typed record. DSC-10's present preparation allowlist also remains restricted to approved source references. This mismatch was raised to the DSC-24 owner. It is unresolved in this branch: no shared schema patch, permissive local reinterpretation, raw-to-native workaround or invented derived record is used to claim acceptance. DSC-24/3 must agree the derived-release lineage/authorization representation and affected owners must adopt it before genuine preparation. DSC-27 also reports that retrospective source-revision availability is unverified: the required shared availability date cannot truthfully be invented as the cutoff. Real release review must remain blocked until that representation/evidence is resolved; mock dates are hypothetical.
2. **Step-7 derived development context.** DSC-28 additionally needs measured derived task/EDA/error summaries and typed upstream preparation/initial records for its LLM context. The current development-only release validator requires availability metadata on every released reference, but those new artifacts cannot retroactively be inserted into immutable preparation. An owner-agreed derived-availability registration or graph representation is still needed; DSC-10 does not bypass that constraint or mutate upstream records.
3. **Genuine approved-packet Codex/Data integration.** The pinned DSC-26 branch already retains genuine isolated synthetic Data execution, artifact retrieval and separate failure evidence. Those engineering probes establish their documented mechanism and scope. This parent branch still needs a complete genuine approved-packet run through the adapter, restricted stage releases, parent adoption and downstream outcomes; a mock-host run does not satisfy that check. Do not invent an external `@Data` API, substitute Code Interpreter or create a separate runtime.
4. **Trusted callback implementations.** Genuine intake consent, content/chronology review and independent evidence review must replace test callbacks. They must bind exact current record versions and measured bytes, operate within finite bounds and avoid parent mutation/reentrancy.
5. **Genuine analytical and verification artifacts.** DSC-27/28/29/30 must supply actual preparation, LLM features, comparable evaluation, frozen November 30 forecast, reserved evaluation, quantity/report and verification evidence. Mock thresholds, treatments and findings do not resolve real task semantics or prove reliability.
6. **Verification stage transport.** DSC-30 produces a check-only record before proposing delivery. Parent registration preserves that one authenticated prior record as an external reference instead of a second current `output_verification` record. Its final proposal must cite the prior reference and exact report. Mock transport passes; safe native release of an external check artifact and failure-draft staging still need an owner-agreed bridge under the same release rules.
7. **Integrated acceptance and durable recovery.** DSC-56/9 acceptance and demonstration depend on genuine upstream outcomes and native blockers. This implementation has in-process pause/review behavior and immutable event bytes, with no process-restart restore support. Any restart/resume mechanism needs a separate DSC-10 design and verification; the current checkpoint must not be deserialized as authority.
