# DSC-60 task construction and limits

[DSC-60](https://linear.app/gr3enarr0w/issue/DSC-60) follows the recorded [DSC-59](https://linear.app/gr3enarr0w/issue/DSC-59) workflow. This change makes intent, context provenance and evaluation discipline explicit. It does not demonstrate that structured prompting improves accuracy.

## Trace before the change

The exact recorded native request is the `turn/start` message in `artifacts/demo/f8567dcea15e473380dbcfc067ccf092/runs/investigation-fd2a074d16e7401ca1682ad64e944847/native/native-rpc.jsonl`. Its user question starts:

> What should I restock in my stores next week? I usually look at the last few months of sales to decide what to buy.

`DemoSession.review` appended the detector's interpretation: the user looks at recent months but supplied no calculation or quantity-setting rule; all four CSVs were inspected without finding another explicit process. `current_process_request` similarly appended manual answers or explicit continuation without a process. `_propose` stored the combined text as both the submission's original request and proposal goal. `backend.run_approved` handed this unchanged proposal to `run_investigation`; `investigation_prompt` labelled the entire combined text “Original question”. The user wording survived, but its provenance boundary was blurred with a derived summary.

The prior prompt already requested autonomous inspection/cleaning/model comparison, no analytical follow-up questions, an honest baseline distinction, mixed/no-improvement reporting, non-LLM routine operation, and separate AI build charges. It already retained December transaction isolation, explicit approval and file identity. Those requirements were not introduced by DSC-60. It did not explicitly request a persisted comparison plan before scores or constrain metric/selection changes after observing comparisons.

In the recorded `output/analyze.py`, six candidates used common targets/origins and a recent-13-week baseline. Minimum seven-day MAE in July–September selected `shared_seasonal`; 14-day scoring was secondary. October–November was labelled “holdout” in that script, but it has now been inspected and must be treated as development evidence. The final `output/response.md` candidly says individual forecasts had about 6% larger errors than the simple average, while October–November totals were closer, and that improvement over the exact customer process cannot be established. Therefore a stronger task structure is a hypothesis to evaluate, not a repair proven to yield forecast gains.

## Changed handoff

The submission now preserves the exact original question, including whitespace. A digest-bound `structured_task_context` proposal assumption stores that question separately from manual process text, explicit continuation, or detector interpretation plus its evidence. The readable composite review and its approval flow remain intact. The machine context is omitted from the displayed assumption list so review stays readable. Existing approved records lacking the context remain usable with provenance explicitly unknown; the code does not attempt to split customer text on invented delimiters.

`task.structured_task` adds a data-scientist role, retail decision objective, attributed context, controller date scope, deliverables and comparison requirements. Data must persist `evaluation_plan.json` before candidate scores, specifying target treatment, missing dates, population, dates/origins, horizons, baseline, candidates, metric/weighting, selection and ties. It must use fair information boundaries, permit the simple baseline to win and preserve original results if the plan changes. The role label alone is not treated as evidence.

No business cost function, customer incumbent or meaningful-improvement threshold is fabricated. Forecast errors cannot establish stock availability or savings without the relevant observations. Useful ordinary analysis may still be delivered when comparisons are mixed or show no gain. Recording a performance-success demonstration remains a separate engineering decision requiring an externally declared threshold, untouched evaluation and independently checked frozen artifacts. This development prompt cannot close it or access December outcomes.

## Verification scope

`tests/demo/test_task.py` checks actual service approval records and injected native dispatch for detected, manual, explicit-absence and Continue-without contexts. It checks exact original wording, detector evidence attribution and withheld December rows. Existing demo tests exercise approval revocation, repeat review, immutable results and output transport. These are deterministic context/transport checks, not a controlled model-quality evaluation. Prompt instructions cannot certify their own execution timing or scientific validity; inspect generated plans, code and results separately.

## Internal native call receipts

`call_trace.begin_call_trace(native_evidence_dir, stage=..., prompt=..., manifest=..., trace_dir=None)` writes exact outbound UTF-8 prompt bytes and a prepared `dsc60-native-call-trace-v1` receipt before dispatch. Its default directory is the sibling `<native-evidence-name>-trace`, leaving the actual native evidence directory fresh and empty as required by the real native policy. An explicit trace directory must remain outside native evidence. `finish_call_trace(receipt, native=native_run)` records thread/turn/outcome links, exposed configuration identity and hashes/paths of native logs; `error=exception` records transport failure. Both detector inspection and analysis stage results reference this receipt. The internal file is also available after native transport failures, without changing customer output or consent.

The receipt distinguishes requested model/medium effort, pinned Data skill/CLI identity, and observed native acknowledgements. It traces explicit inputs and exposed evidence only. It does not claim knowledge of hidden/system instructions. Historical prompts under `evidence/demo/dsc60-debug-2026-10-20/trace/` were extracted from stored sent RPC events; those logs pass through the existing projection/sanitization layer, so their hashes identify the exposed stored prompt, not an asserted pre-sanitization or complete model-context capture. The compact index retains the original question, exact detector quote and native source hashes without copying transaction rows.

## Optional controller comparison contract

Ordinary analysis keeps autonomous target/baseline/metric selection when `comparison_contract=None`. Authorized engineering runs may construct `DemoSession(comparison_contract=definition)` with exactly these required nonempty text definitions: `target`, `baseline`, `primary_metric`, `population`, `dates`, `forecast_horizon`, and `selection_rule`; `secondary_diagnostics` is optional. Missing, empty or unexpected fields fail before approval. The controller provides every definition; the app never infers these engineering settings from customer or detector text. `set_comparison_contract(definition)` validates and copies a changed setup, revoking old approval and results. Caller mutation cannot change a copied setup.

The context wraps the complete definition with provenance `engineering_comparison_not_customer_fact` and SHA-256 of sorted compact UTF-8 JSON. Existing proposal digest/consent binds this context. Review discloses the fixed comparison in plain language without technical protocol details. The outbound brief requires the original target, baseline, metric, population, periods, horizon and selection rule throughout; alternatives remain secondary sensitivity diagnostics. Data must record the unchanged definition and digest as `comparison_contract_sha256` in its evaluation plan, retaining selection evidence. If unsupported, report incompatibility rather than silently changing the setup. Echoing a digest demonstrates recorded adoption only; code/results still require independent semantic and calculation checks. No untouched-data or business-success claim follows from this engineering development contract.

After native execution, `inspect_comparison_plan` safely reads at most 64 KiB from `evaluation_plan.json`, refuses symlinks and retains readable plan bytes in the immutable artifact store even when JSON is malformed or the declaration mismatches. Stage metadata `comparison_plan` records expected/declared digest, exact wrapper equality, immutable plan reference and status `recorded`, `missing`, `mismatch`, `invalid` or `not_requested`. Future requested plan schema requires `comparison_contract` to equal the full wrapper and `comparison_contract_sha256` to equal its digest. `recorded` means declared adoption only: it does not establish when the plan was written, semantic/code/calculation compliance, forecast benefit or recording readiness. Inspection status does not block a useful CSV or promote verification. Previously running experiments retain their actual schema/results and are not automatically rerun.

## Refining the decision within Data

The customer's existing method is context and an incumbent comparison when it can be evaluated. It is neither a requirement to reproduce its mechanics nor a ceiling on the proposed solution. Data should identify the underlying decision, available actions, decision unit, horizon and desired outcomes from the question and evidence, while keeping supplied priorities distinct from inferred tradeoffs and unknowns. It cannot invent missing buying rules, business cost functions or success thresholds.

The structured brief assigns this refinement and planning to Data inside the already-approved analytical turn. It requests internal `task_refinement.json` before candidate scoring, with the refined task separately attributed and original question/context preserved. This introduces no separate prompt-engineering agent, customer-specific rewriter before approval or additional model call. Candidate rationale should cite released files and code observations, rather than turn the customer's description into a fixed solution specification.

Ordinary MVP discovery covers lightweight conventional CPU-only predictive forecasting models, compared against a fair simple baseline. The user’s “simple” guidance means roughly below random-forest complexity and practical operation on an ordinary computer with 8 GB RAM; it does not limit candidates to averages or a few formulas. Data can discover justified candidates without a hardcoded six-model list or predetermined winner. Neural/deep-learning models, heavy ensembles, expensive unbounded search, operational redesign and nonpredictive policy optimization remain outside scope.

Assess actual dependencies, data size, preparation, retained arrays/models and both fitting and inference workload. Report measured or justified runtime and peak-memory needs, with assumptions and limits, allowing room for the operating system on the target computer. Neither a model name nor execution on the current host proves 8 GB compatibility; the current host’s memory must not be assumed to be 8 GB. Routine calculations must use no paid model/API calls. Keep routine costs separate from AI-assisted analysis/build costs. Practical suitability assessment does not authorize a different operational solution. Select through a fair measured comparison, permitting the baseline to win. The customer’s current method remains contextual comparison rather than a ceiling on supported lightweight forecasting alternatives. Controlled engineering contracts retain their authorized scope unchanged.

The initial candidate set and comparison plan precede scores. Evidence-driven development iteration is permitted if each new comparison has a prospective versioned plan recording its rationale, prior development evidence and changed choices; retain earlier plans/results and label follow-on results exploratory. Keep the fair baseline and primary comparison stable, avoid reserved evaluation outcomes and do not keep searching merely until a gain appears. In controlled engineering regression/replay mode, the explicit contract's authorized candidate scope and comparison remain fixed; the refinement responsibility inspects only authorized alternatives and records other possibilities as out of scope without scoring or promoting them. Discovery cannot silently broaden that controlled experiment. Neither planning nor prompt wording establishes actual compliance or improvement.

## Separate business-writing turn

After completed Data analysis, `backend.run_approved` calls `business_response.run_business_response` in a fresh native stage using the same public GPT-6.1-sol/medium configuration. This is a genuine additional LLM prompt on each successful run, not deterministic wording substitution. Its release contains only the immutable original explanation, bounded optional measured/comparison/evaluation/workload context and computed CSV hash/count facts. It receives no raw sales, CSV rows, fitted model or earlier workspace access. The stage requests practical outcomes, an accurately named baseline and measured gain, useful actions and a clear explanation of repeated calculations the local routine handles. New monthly data is described only as a possible improvement/monitoring opportunity; hours, savings, deployment and integration are not invented.

The writer preserves original analysis and CSV/HTML/model bytes. It writes a new Markdown narrative plus a result binding the source-manifest and narrative hashes. Exact outbound prompt, source manifest, native evidence, rewrite result and response have immutable references connected by the internal writing receipt. Current browser consent is checked before staging/dispatch and after the turn. There is no healthy-run deadline; native transport controls and cancellation remain available. A writer failure retains the useful original explanation and records its error internally without adding a customer warning. Revoked consent still prevents publication. Narrative hash/schema checks establish identity and lineage, not independent analytical verification.

For an already completed run, call `run_business_response(store, stage_result, fresh_work_root, current_consent_callback)` using its retained investigation `stage_result` and original ArtifactStore. It creates a new sibling stage without refitting or editing the completed run. Publication into an app or a final acceptance decision remains a separate current-state action. Unit tests use explicit fake hosts; they do not count as a genuine writing run.

The final December continuation is retained in `evidence/demo/dsc60-debug-2026-10-20/final-evaluation/`. The exact selected fitted model and baseline forecasts were committed/pushed before outcome release. Genuine Data and a separately authored verifier agree on 4.060186% lower recorded-unit weekly MAE than the same recent13 baseline across four fixed December windows, with lower error in every week. This is a qualified reserved-period result: earlier pooled full-history profiles were exposed, only 35.4% of cells have seven observed days, and bias worsens. It does not establish pristine untouched validation, an exact customer-process comparison, purchasing savings or parent acceptance. No tuning or candidate promotion followed the outcome release.

The final actual writer pass gives a plain model description using bounded `task_refinement.json` alongside completed results; completed results take precedence over old planning-status assertions. It concentrates on practical output, measured accuracy, automated arithmetic and routine costs, with compact purchase checks. It does not ask for newer data or require more data to complete the MVP. Exact first and revised writer outputs are retained, including the first pass's independent user-fit rejection.
