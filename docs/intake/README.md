# DSC-25: understanding and sign-off conversation

This component receives the user's original retail restocking request and actual supplied references, forms a proposal using bounded read-only inspection, presents the parent-reviewed proposal, and records the user's response against that exact version. It returns the same approved proposal for the parent to use. It performs no analytical preparation and owns no execution transitions.

The assignment is [DSC-25](https://linear.app/gr3enarr0w/issue/DSC-25). Application paths use the exact DSC-25 reservation in [DSC-3's published ownership map](../architecture/OWNERSHIP.md). Shared records use DSC-24's pinned [`0.1.0-draft.3` snapshot](../contracts/SNAPSHOT.json), without a consumer schema fork. The `RetailUnderstanding` and humanizer output shapes are local model-output validation shapes, not additional wire contracts. A fresh owner acknowledgment and the dependency request were sent to DSC-3; no new acknowledgment is inferred here and no shared file is edited.

## Prompts and focused calls

The executable prompt source is [`roles.py`](../../src/suiroai/intake/roles.py): `UNDERSTANDING_PROMPT` restates the user's goal and separates supplied facts, supported interpretations, synthetic assumptions and unknowns; `HUMANIZER_PROMPT` explains the versioned proposal and actionable gaps in plain language. Keep those constants authoritative when changing behavior. `NEEDS` defines the retail business inputs and why each is needed.

`build_langchain_roles(model)` composes two focused `ChatPromptTemplate | model.with_structured_output(...)` calls. The caller supplies the configured model. Neither call has tools, analytical execution authority or an autonomous agent loop. There is no fallback runtime. Provider/model configuration, credentials, timeout policy and shared manifest/lock dependencies belong to the deployment/DSC-3 owner. A mocked `.invoke()` result verifies component behavior only; it does not establish a live LangChain/provider invocation.

## Receipt and inspection boundary

[`receive_submission`](../../src/suiroai/intake/receipt.py) reads only explicitly listed `SuppliedFile` references. It never discovers or substitutes the prepared retail fixture. An empty list remains an empty submission. A missing local path is recorded as `missing`; an unreadable file or unsupported remote reference is `inaccessible`. A trusted connector can provide a bounded `read_bytes(file, limit)` function; the default reader does not download remote references.

Receipt measures exact bytes, SHA-256, size and the declared file version. Its bounded inspector reads a CSV header, identifies candidate `Product_ID`/`Store_ID` fields and, for a declared dictionary, previews at most 40 dictionary records. This is source inspection metadata. It does not validate row completeness, field meaning, stock coverage, join compatibility or readiness for analysis. It performs no joins, cleanup, aggregation, feature construction or modeling. Limits are 64 uniquely identified references, 16 MiB per file and 64 MiB total by default; rejected oversized inputs remain explicit and request an accessible bounded extract.

An `Inventory_Level` header does not establish usable stock; `Delivery_Days` does not establish supplier lead time. Absent inbound rows do not establish zero open orders. Missing product/store dates do not establish zero demand. The known demo's synthetic operating facts enter a conversation only through actual supplied/authorized inputs with their provenance. Business facts are requested when material; target treatment, imputation, algorithms and hyperparameters remain agent decisions.

## Structured outputs and host responsibilities

| API | Returned artifact | Responsibility retained by caller/parent |
| --- | --- | --- |
| `receive_submission(...)` | Immutable `Receipt` snapshot: shared submission, measured source refs and inspection metadata | Allocate task/input/file versions; authorize reference access; retain measured bytes |
| `draft_proposal(receipt, understanding=..., proposal_version=..., clarifications=())` | `ProposalDraft` with shared `task_proposal` or an unsupported-task understanding | Allocate proposal version; supply actual attributed clarification events; independently review semantics against original sources |
| `present_proposal(..., humanizer=..., parent_review=...)` | `Presentation` packet with exact proposal, customer message, status and review digest | Check the exact packet and measured source information before presentation; return literal `True` only after independent review |
| `capture_response(..., response=..., current_submission=..., current_proposal_ref=..., approval_version=...)` | `ConversationResult` with shared `task_approval`, status and customer response | Authenticate actor/event, classify ambiguity conservatively, supply authoritative current versions and allocate approval version |
| `approved_handoff(...)` | Same `[submission, task_proposal, task_approval]` chain | Enforce state, approval authority, execution bounds and all execution transitions |

Snapshot properties deserialize detached copies. Their mutability does not change the captured proposal. Coverage claims must cite measured accessible file IDs and existing columns, or an exact original-request quotation. Citing a header checks evidence identity, not factual sufficiency. `parent_review(packet, receipt)` is a trusted integration boundary: it must inspect the actual source information and independently verify material claims and customer wording. An echo callback or the generating model's self-check is not that review.

The packet separates conversation `status` from `capability`. A ready proposal with supported interpretations or synthetic assumptions reports `ready_with_assumptions` while still `awaiting_confirmation`. The shared proposal retains DSC-24's `ready` enum. Missing quantity meaning/review context alone requests `needs_material_facts`; missing operational inputs report `needs_inputs`. Every focused call has a 128 KiB serialized-context limit; dictionary previews also have an 8 KiB limit. Oversized context raises an intake error before model invocation.

The proposal carries goal, intended output, source references, version/input bindings, provenance, assumptions, gaps and temporal constraints. Missing required coverage or inaccessible inputs adds actionable blocking gaps. Row/target investigation and the acceptance rule remain explicit internal pending work; the customer is not asked to choose statistical treatments. Requests outside the single historical retail restocking task return `unsupported_task`, without routing or silently changing the request.

`Response` is a trusted host event, not an LLM approval prediction. `reply_to` must be the current exact `record_ref(proposal)`. An approval containing corrections or new material is a revision. A bare JSON approval record is not authenticated consent. No response (`None`) and an unclear reply both remain pending. An attempted approval while required inputs/business facts are missing remains pending with the actionable gap status. Explicit rejection, correction or new material returns `revise_proposal`; the parent repeats step 2 with revised versions and seeks fresh sign-off. Stale proposal/input references fail closed.

See [MOCK conversation examples](mock_conversations.json) for absent, inaccessible and partial inputs, faithful restatement, correction/new-data loops, stale approval and waiting. These are illustrative UI/status excerpts, not complete shared-schema records, genuine uploads, live model outputs or integration acceptance evidence. Complete shared-contract mock chains remain owned by DSC-24 under [`examples/contracts/v0.1.0`](../../examples/contracts/v0.1.0/).

## DSC-10 and DSC-26 integration

The coordinated parent API is `ParentWorkflow.receive_submission(submission, external_refs=measured_refs)`, `present_proposal(proposal)`, `record_approval(approval)` and `start(execution)`. DSC-10 owns its implementation and authoritative monotonic versions. Receipt/proposal generation does not advance that workflow. On correction or material input, the host gives the parent a new submission/version and repeats understanding/presentation; it must not reuse the old approval.

Draft.3's submission-file inventory has no file-version field. Actual source versions remain in `Receipt.sources` and proposal `source_refs`; the parent must increment `input_version` on a material file revision even when the measured bytes/hash are unchanged. On a correction, retain the original request verbatim and pass the actual host-authenticated `Response` events through `clarifications`. The focused call receives those attributed events alongside the original request; their literal text, actor, timestamp and prior proposal reference are retained as supplied-fact context in the revised proposal. The parent must allocate a revised task/proposal binding and retain its source-review/consent ledger. The intake component cannot allocate authoritative revisions or authenticate resumed records.

The parent constructor's `confirm_approval(approval, proposal) -> literal True` callback authenticates the actual DSC-25 consent event and exact presented version. It cannot trust arbitrary JSON alone. The host retains the presentation and authenticated event as evidence for this check. DSC-25's `parent_review` callback and DSC-10's `confirm_approval` have different jobs: source/wording review before presentation, and consent authentication when recording approval.

`approved_handoff` returns the captured records unchanged. No task-definition call follows approval. The parent allocates the run and bounded execution contract, checks the approved chain, and constructs stage requests for DSC-26's existing [`StageAdapter`](../integration/ADAPTER.md). DSC-25 does not instantiate or invoke that adapter, authorize an analytical stage, approve checkpoint claims, or deliver a final analytical report. DSC-26 still requires measured stored external bytes and trusted parent permission/review callbacks.

The November 30, 2025 forecast context and reserved December evaluation are part of this one task. Original source receipt is not permission to expose unrestricted future rows to feature generation/model selection. Post-approval preparation and the parent must release only the permitted development artifacts to those consumers; this intake component does not create the partition.

## Behavioral checks and remaining acceptance

Meaningful component checks should exercise actual receipt with absent/missing/inaccessible/partial supplied references; reject fabricated file/column evidence; retain request/context/provenance; distinguish missing inputs from role/infrastructure failures; reject unreviewed presentation; and exercise rejection, correction, material-new-data, pending and stale-version responses. A successful handoff must retain the exact proposal content/reference/digest, and inspection must not invoke analytical preparation or an execution adapter. These checks use explicitly mocked focused-role outputs unless separately labeled as live evidence.

Passing component/mock checks does not establish end-to-end execution acceptance or close DSC-25. The real handoff still requires DSC-10/26 integration with authenticated consent, measured sources, independently reviewed wording and the unchanged approved proposal. Live LangChain/provider behavior and shared dependency integration require their actual owner/configuration. Source semantic sufficiency is a trusted parent review responsibility; schema/header checks alone cannot prove it. The conversation is stateless and intentionally has no durable consent ledger, resume logic, run controller or customer delivery channel. Their implementations remain with the parent/host owners. Source metadata inspection is bounded and may be partial; analytical data-quality findings await approved preparation. No issue-status change is justified by the illustrative examples or mocked checks.
